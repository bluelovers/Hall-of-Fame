從 PHP 5.6 跨越到 7.x 甚至 8.x 的巨大變化，整理了一份詳細的相容性比較表。

這份表格重點在於「直接影響程式碼能否執行」的關鍵差異：

### PHP 5.6 vs. 7.x vs. 8.x 相容性對照表

| 比較項目 | PHP 5.6 系列 | PHP 7.4 (中繼站) | PHP 8.x (現代標準) |
| --- | --- | --- | --- |
| **資料庫支援** | 支援 `mysql_*` | **徹底移除 `mysql_***`，僅支援 `mysqli` / `PDO` | 延續 7.4，僅支援 `mysqli` / `PDO` |
| **建構子寫法** | 支援與類別同名函數 | 廢棄同名函數，建議 `__construct` | **徹底移除**同名函數，必用 `__construct` |
| **錯誤處理** | 傳統報錯 (Notice/Warning) | 引入 `Throwable` 介面 | 許多 Warning 變更為 **Fatal Error (崩潰)** |
| **變數解析** | 舊式解析邏輯 | 統一變數語法 (可能影響 `$$var`) | 嚴格解析，不容許歧義 |
| **動態屬性** | 隨意使用 `$this->undefined` | 正常使用 | **廢棄** (8.2+)，必須先在類別定義屬性 |
| **字串/數字比較** | `0 == "foobar"` 為 **true** | 同 5.6 | `0 == "foobar"` 為 **false** (更符合直覺) |
| **十六進位字串** | 視為數字 (`"0x10" == 16`) | **不再視為數字** | 同 7.4 |
| **效能 (基準)** | 1x (最慢) | ~2.5x (大幅提升) | **~3x - 4x** (JIT 編譯器加入) |
| **安全性** | 極低 (官方停止維護多年) | 低 (已停止維護) | **最高** (持續修補漏洞) |

---

### 三大升級地雷區 (具體影響分析)

#### 1. 資料庫連線 (最大的斷層)

* **5.6 程式：** 滿滿的 `mysql_connect()`、`mysql_query()`。
* **7.0 以後：** 這些函式**完全消失**。如果你的原始碼裡有這些字眼，直接搬到 PHP 7/8 會出現 `Fatal error: Uncaught Error: Call to undefined function mysql_connect()`。
* **對策：** 必須將所有 `mysql_` 改寫為 `mysqli_`（通常函式參數順序也要調整）或 `PDO`。

#### 2. 對於「不嚴謹寫法」的容忍度

* **5.6 時代：** 變數沒定義就拿來加減、陣列索引寫錯，通常只會出一個 Notice，網頁還能動。
* **8.x 時代：** 核心變得非常「嚴格」。以前會過的部分，現在可能直接報 **Fatal Error** 導致整個網頁變白板。這也是為什麼 5.6 程式碼很難直接在 8.x 執行的主因。

#### 3. PHPUnit 的對應關係

如果你要幫這些版本的原始碼寫測試，PHPUnit 的選擇也非常破碎：

* **PHP 5.6：** 只能用 **PHPUnit 5.7** (Phar)。
* **PHP 7.4：** 最高支援到 **PHPUnit 9**。
* **PHP 8.2+：** 必須使用 **PHPUnit 10 或 11**。

---

### 總結建議

1. **如果你只是想稍微提升效能並維持相容性：** 升級到 **PHP 7.4** 是最痛點最少、收穫最大的選擇（除了改資料庫連線外，其他多半能動）。
2. **如果你追求極致安全與效能：** 你必須在 **PHP 8.x** 環境下重寫或大量修復舊程式的語法錯誤。
