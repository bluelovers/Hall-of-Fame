# BUG-004: 測試套件狀態汙染 — Windows PHP 5.6 `flock()` 鎖殘留導致 `file_get_contents()` 回傳空字串

> 建立日期：2026-05-12
> 修復日期：2026-05-12
> 狀態：✅ 已修復

---

## 問題描述

**檔案**: `test/phpunit/YamlLoadTest.php`, `test/phpunit/PatternTest.php`
**類型**: 測試隔離性失敗 / 狀態汙染（State Contamination）
**環境**: Windows PHP 5.6.32 (nts, Win32, VC11, x64)

### 症狀

`YamlLoadTest::testDirectYamlLoad()` 在單獨執行時通過，但在全量測試套件（33 tests）中失敗：

```
1) YamlLoadTest::testDirectYamlLoad
YAML data should not be empty
Failed asserting that a NULL is not empty.
```

### 重現步驟

```bash
# ✅ 單獨執行 — 通過
php-test phpunit/YamlLoadTest.php

# ❌ 全量執行 — 失敗
php-test phpunit/
```

---

## 調查過程（7 個階段）

### Phase 1: 表面症狀確認

**症狀**: `HOF_Class_Yaml::load($file)` 回傳 `null`。

在 `Symfony_Component_Yaml_Yaml::parse()` 中，當傳入檔案路徑字串時，內部呼叫 `file_get_contents($file)` 回傳空字串 `""`，Parser 解析空內容後回傳 `null`。

```php
// Symfony/Component/Yaml/Yaml.php:33
$input = file_get_contents($file);  // ← 回傳 "" 而非 false
$yaml = new Symfony_Component_Yaml_Parser();
return $yaml->parse($input);        // ← 解析空字串 → null
```

### Phase 2: 測試汙染源確認

**方法**: 在全量執行中加入詳細診斷輸出。

```php
echo "  file_exists: " . (file_exists($file) ? 'Y' : 'N') . "\n";
echo "  is_readable: " . (is_readable($file) ? 'Y' : 'N') . "\n";
echo "  filesize: " . filesize($file) . "\n";
```

**結果**:
```
file_exists: Y
is_readable: Y
filesize: 433
load() result type: NULL
```

檔案存在、可讀、且有 433 bytes，但讀取回傳空。

### Phase 3: 檔案讀取方式交叉測試

**方法**: 比較四種不同讀取方式的結果。

```php
// 方法 1: file_get_contents
$content = file_get_contents($file);
echo "  file content length: " . strlen($content) . "\n";        // → 0

// 方法 2: fopen + fread
$fh = fopen($file, 'rb');
$fread_content = fread($fh, filesize($file));
echo "  fopen+fread content length: " . strlen($fread_content) . "\n";  // → 0

// 方法 3: realpath + file_get_contents
$real = realpath($file);
$rp_content = file_get_contents($real);
echo "  realpath file_get_contents length: " . strlen($rp_content) . "\n";  // → 0

// 方法 4: copy 到暫存檔
$tmp_copy = sys_get_temp_dir() . '/hof_debug_char_copy.yml';
copy($file, $tmp_copy);
$copy_content = file_get_contents($tmp_copy);
echo "  copy to temp length: " . strlen($copy_content) . "\n";   // → 433 !! ✅
```

**關鍵發現**:
| 讀取方式 | 結果 | 說明 |
|---------|------|------|
| `file_get_contents()` | 空字串 | 失敗 |
| `fopen() + fread()` | 空字串 | 失敗 |
| `realpath()` + `fopen()` | 空字串 | 排除路徑解析問題 |
| `copy()` + `file_get_contents()` | **433 bytes** | ✅ 成功 |

`copy()` 能成功讀出內容，但 `file_get_contents()` 和 `fread()` 不行。這表示問題不在檔案系統層，而在 PHP 串流讀取機制。

### Phase 4: 排除 stat 快取干擾

**方法**: 在每次讀取前加入 `clearstatcache(true, $file)`。

```php
clearstatcache(true, $file);
$content = file_get_contents($file);  // → 仍然是空字串
```

**結論**: 不是 PHP stat 快取的問題。

### Phase 5: 排除路徑解析問題

診斷輸出顯示路徑包含 `config/../../trust_path/` 的相對路徑元件。

**方法**: 使用 `realpath()` 解析為標準絕對路徑後再讀取。

```php
$real = realpath($file);
```

**結果**: `realpath()` 成功解析出標準路徑，但 `file_get_contents($real)` 仍然回傳空字串。

**結論**: 問題與 `config/../../trust_path/` 路徑無關。

### Phase 6: 對照正常測試確認差異

`testSourceDataBeforeSetCharData()` 和 `testFullLoadChain()` 在**同一個測試檔中、同一失敗之後**仍然通過。

**方法**: 比對兩種程式碼路徑。

```php
// testDirectYamlLoad（失敗）:
// 路徑 A: 傳入字串路徑
HOF_Class_Yaml::load($file_path_string)
  → Symfony::parse($file_path_string)
    → file_get_contents($file_path_string)   // 失敗

// testSourceDataBeforeSetCharData（通過）:
// 路徑 B: 透過 HOF_Class_Char::factory()
  → Char::source()
    → fplock_file($this->file)               // 開啟檔案資源
    → HOF_Class_Yaml::load($this->fp)        // 傳入資源 (is_resource=true)
      → fp_get_contents($this->fp)           // 使用 fread + rewind ✅
```

**結論**: `testDirectYamlLoad` 走的是「字串路徑」→ `file_get_contents()` 的 code path，而其他測試走的是「檔案資源」→ `fp_get_contents()`（內部 `rewind + stream_get_contents`）的 code path。兩條路徑完全不同，前者的鎖殘留問題不影響後者。

### Phase 7: 確認根源為前導測試的鎖殘留

**方法**: 在測試開頭加入全體清理。

```php
// 在 YamlLoadTest::setUp() 中加入
HOF_Class_File::fpclose_all();   // ← 加上這個後通過
clearstatcache();
```

**結果**: ✅ 通過。確認前導測試（PatternTest）透過 `fplock_file()` 開啟並鎖定的檔案句柄在 `fclose()` 後，Windows 層的 `flock(LOCK_EX)` 鎖未即時釋放，影響後續 `file_get_contents()` 的讀取。

## 根因分析

### 直接原因

**Windows PHP 5.6 上 `flock(LOCK_EX)` + `fclose()` 後的鎖殘留。**

PHP 的 `flock()` 在 Windows 上是透過 Win32 API `LockFileEx()` 實現。當檔案以 `r+` 模式開啟並取得獨占鎖（`LOCK_EX`）後，即使 PHP 層呼叫了 `fclose()`，Windows 核心層的鎖不會立即釋放給同一個行程的其他開啟嘗試。

### 完整觸發鏈

```
PatternTest::setUp()
  → HOF_Class_Char::factory()
    → Char::source()
      → HOF_Class_File::fplock_file($file)    // fopen("r+") + flock(LOCK_EX)
      → HOF_Class_Yaml::load($this->fp)         // 以資源方式讀取成功

... PatternTest 測試執行 ...

PatternTest 結束（TestCase 物件被回收）
  → Char::__destruct()
    → HOF_Class_File::fpclose($this->fp)        // fclose() + unset(本機變數)
      → Windows 核心層鎖未即時完全釋放          // ← 關鍵問題點

YamlLoadTest::testDirectYamlLoad()
  → HOF_Class_Yaml::load($file_path_string)
    → file_get_contents($file_path_string)       // → 回傳空字串！
```

### 為什麼 `copy()` 可以成功

`copy()` 在 Windows PHP 內部使用 Win32 API `CopyFileW()`，這是作業系統層級的檔案複製函式，**完全繞過 PHP 的 stream wrapper**，直接與 NTFS 檔案系統互動。因此不受 PHP `flock()` 鎖殘留的影響。

### 為什麼其他測試不受影響

`testSourceDataBeforeSetCharData()` 和 `testFullLoadChain()` 透過 `HOF_Class_Char::factory()` 載入角色，內部使用 `fplock_file()` 取得檔案**資源**再傳給 `HOF_Class_Yaml::load($this->fp)`。這走的是 `is_resource_file()` 分支 → `fp_get_contents()`（`rewind + stream_get_contents`），繞過了 `file_get_contents()` 的 code path。

## 解決方案選項評估

### 方案 A：測試檔案 `.setUp()` 全體清理 ✅（採用）

**作法**: 在 `YamlLoadTest::setUp()` 中呼叫 `HOF_Class_File::fpclose_all()` + `clearstatcache()`。

**優點**:
- 變更範圍最小（僅限測試檔）
- 不修改生產程式碼
- 原理正確：測試獨立性

**缺點**:
- `fpclose_all()` 可能觸發已關閉資源的 `fclose()` 警告（`@` 抑制但仍會被 PHPUnit 捕獲）
- 是治標而非治本

### 方案 B：改用資源路徑繞過字串路徑 ❌（未採用）

**作法**: 修改測試改用 `fplock_file()` + `fp_get_contents()` 方式讀取。

**優點**: 與生產程式碼走相同 code path，確保不會有此問題。

**缺點**:
- 測試意圖偏移：本來要測「字串路徑」的 `HOF_Class_Yaml::load()`
- 字串路徑的 code path 永遠不會被測試到
- 測試不再驗證完整的 `HOF_Class_Yaml::load()` 行為

### 方案 C：前導測試 `.tearDown()` 明確釋放 ✅（採用）

**作法**: 在 `PatternTest::tearDown()` 中設定 `$this->char = null` 觸發 `__destruct()` → `fpclose()`。

**優點**:
- 從源頭解決：確保前導測試的資源在測試結束時立即釋放
- 良好的測試習慣：每個測試應清理自己的資源

**缺點**:
- 不確定是否能獨立解決（與方案 A 配合效果最好）

### 最終方案：A + C 聯合

**A + C 合併使用**，同時達到：
1. **源頭清理**（C）：PatternTest 結束時立即釋放 char 資源
2. **防禦性清理**（A）：YamlLoadTest 開始前強制清理所有殘留資源

## 最終修復內容

### 修改檔案 1: `test/phpunit/PatternTest.php`

```php

{

}
```

## 經驗教訓

1. **`file_get_contents()` ≠ `copy()`**: 兩者在 Windows 上使用不同的底層 API，表現可能不一致
2. **Windows `flock()` 行為**: PHP 的 `flock()` 在 Windows 上透過 `LockFileEx()` 實現，鎖釋放行為與 Linux 不同 — `fclose()` 後鎖可能不會立即完全釋放
3. **測試隔離性**: 測試依賴執行順序是危險訊號。即使單獨測試通過，也不代表全量測試時不會被汙染
4. **HOF_Class_File 的快取設計**: `self::$data` 是「檔案句柄註冊表」而非一般快取，`fpclose()` 的 `unset($data)` 僅取消本機變數（設計使然），主要清理由 `fpclose_all()` 在請求結束時進行
5. **資源路徑 vs 字串路徑**: HOF 中存在兩條 YAML 載入路徑（資源 vs 字串），行為不一致。未來應考慮統一為資源路徑以避免類似問題
